# 新资料的收录判断

## 决策所需信息

结合用户当前目标，判断内容能否被长期复用、是否已有相同来源、描述谁、是否完整可信，以及用户是否授权长期保存。不要用一个模型“置信分”替代这些判断。

| 决定 | 典型情形 | 动作 |
| --- | --- | --- |
| 收录 | 用户明确要求保存，或当前可信授权覆盖此类原始内容 | 直接执行支持的导入，附真实来源并检查任务 |
| 询问 | 材料有长期价值，但用户只要求当前阅读；归属或收录范围影响处理 | 给出具体用途，只问一个会改变动作的问题 |
| 跳过 | 寒暄、临时查询、无用重复、未被采纳的模型生成内容 | 完成当前任务即可，通常不专门通知 |
| 暂缓 | 凭据、越权内容、来源不明、文件缺失、无法访问或解析失败 | 不复制到长期库；说明当前任务的限制或可行下一步 |
| 关联已有资料 | 已确认是同一份原件或是旧材料的补充 | 复用已有来源；新版本不能直接覆盖旧版或人工决定，按实际能力处理 |

这张表指导“值得保存”和“是否有权保存”两项独立判断。有价值不等于有授权；用户明确要求保存且内容可处理时，也不用再推销一次价值。

## 归属和重复

- 上传者、文中人物和论文作者分别判断。只有用户明确说明资料描述本人时，才传 self；其余用 reference。
- 先查目录/检索可能的已有来源，再按需要读取原文。文件名、标题或 URL 相同不证明内容相同；关键词搜索未命中也不证明不存在。
- 当前来源列表和上传结果包含原件 SHA-256；只有同库原件哈希和长度均一致时才判断内容相同。上传重试用相同 request_id 避免重复来源，不同请求不会自动合并；不提供文件版本合并接口。证据不足时不宣称“已去重”或“已更新原版本”。确为不同版本时保留差异，向用户说明当前会新增来源；不删除旧版。
- 摘录、网页转载和部分解析只能代表覆盖到的内容，不能用于完整论文总数等全量结论。

## 不同输入的处理

| 输入 | 当前可执行的方式 | 不应宣称的结果 |
| --- | --- | --- |
| 用户授权保存的原始文字 | import_text，沿用一次操作的 request_id；轮询任务并读回 | 仅凭 202 或收到 job_id 就说可检索 |
| 已上传到知序的文件 | 读取资料/处理状态，利用现有后台增量目录 | 再造一个同内容文本来源或重复问同一入库授权 |
| 聊天附件或用户指定的本机文件 | 确需收录且已授权时，prepare_file_upload → 宿主复制指定文件 → upload_file → get_job；宿主无法取得原件时才引导网页上传 | 把模型摘要通过 import_text 导入后说原 PDF/Office 已保存 |
| 网页链接 | 可按当前请求读取公开内容；是否长期收录单独判断。当前没有链接抓取/原件下载 MCP 工具 | 只保存 URL 就说全文已下载、已归档 |
| 用户选中的网页原文 | 经授权可按原文转录为文本，注明用户提供的 URL、获取方式和实际覆盖范围 | 把转录文本描述为完整网页快照 |
| Agent 生成的总结 | 有实际证据且用户要求保存时，save_knowledge_page 保存为生成专题 | 回灌为原始事实；为日常目录维护反复新建页面 |

如果必须原样保存文件或网页、而宿主只有文本工具，不偷偷改为摘要入库。保留用户原始材料的位置，只说明该动作尚未完成；暂缓不是创建了持久待收录队列。

## 原文件上传

1. 先核对知识库身份。调用 prepare_file_upload 查看本人容量、2 GiB 上限和 staging_directory。用户已明确要求入库时不重复询问相同授权；聊天里仅用于阅读的附件不自动取得长期收录授权。
2. 使用 WorkBuddy 正常的文件工具，将用户指定的那一份原文件完整复制到该目录的直接子文件。保留原件；不遍历磁盘、不放符号链接或硬链接、不关闭沙箱。这个中间复制由助手完成，不要求用户复制命令。无法访问文件就说明限制，不通过 MCP 读取其他路径。当前仅支持同电脑 stdio，远端服务无法读取本机附件路径。
3. 调用 upload_file(local_path=绝对路径, request_id=本次稳定UUID, filename=原附件名, subject_scope=reference或self)。只在用户明确说材料描述本人时用 self。原件字节直接由连接程序按分块传输，不在模型上下文中展开 Base64；PDF、Word、Excel、PPT、图片等统一使用原件入库管线，实际解析覆盖仍须检查。收录原件不要求先在宿主解析文件；不为上传安装 PDF 解析器或 OCR，后台负责解析。
4. 记录 upload_id、source.id 和 job_id。返回 sha256_verified 表示原件一致，不代表解析完整。使用 get_job 等待后台，随后读取目录、read_source 或检索核验。已有目录/人工修改继续使用，不另造摘要来源。
5. 网络中断沿用相同文件与 request_id 重试；上传位置由服务端恢复。明确的权限/参数/内容冲突不反复重试。read_file_upload 可查看收到的字节与状态；不再需要时用 cancel_file_upload 取消尚未完成上传、释放预留，它不删除已入库来源或本机文件。文件变化或上传过期时使用新 request_id；不要复用旧标识混传不同内容。

上传不会删除本机原件或收件副本。工具尚未出现在当前 WorkBuddy 工具表时，只需正常重连该 MCP；不能改用直接 HTTP、读凭据或重新安装其他知识库来假装完成。

## 执行与核验

导入前确定标题、原始内容、归属及授权依据；必要时只询问不确定项。重试沿用原 request_id，内容变化必须作为新操作。不要把令牌、密码、验证码写入资料、进度记录或回答。

get_job 返回 completed 后，再通过目录或 read_source 确认可用。本轮最多作三次短间隔状态查询；仍未完成就返回 job_id 和 queued/running 状态，不高频无限等待，也不把未完成判为失败。失败时说明失败原因，不再重复导入同一内容来“修复”。

若导入请求超时、结果未知，本轮可用原 request_id 重试一次；仍不确定就保留该 ID 并报告结果未知，避免换 ID 制造新来源。明确拒绝、鉴权失败或参数错误不按超时重试。当前任务状态为 failed 或 cancelled 时停止等待并解释下一步。

## 用户引导示例

- 合适：“这份项目验收记录能支持以后填写项目经历，需要一起放进知识库吗？”
- 已授权时：“按你刚才的要求，我会保存这份最终版纪要，并检查目录更新。”
- 无需提示：“今天几号”“把这句话翻译一下”等没有长期资料价值的请求，直接完成。
- 用户说“这次不存”：仅完成本次任务，本会话不反复询问；不自行创建一份临时落盘副本。
