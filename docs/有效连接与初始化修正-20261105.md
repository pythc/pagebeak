# 有效连接直接初始化：0.13.8 修正

2026-11-05，修正已发布到 [正式开始页](https://zhixu.110-lab.cn/start)。这台电脑已安装的同名助理也已更新到 `0.13.8`，通过 WorkBuddy 自带校验和注册脚本；原 `.mcp.json`、其他专家注册项不变。

## 为什么上一版仍然停住

用户反馈，当前 WorkBuddy 会话发现和调用 `workbuddy_request_mcp_connection` 均不可用，但已有资料连接实际生效，并通过同源校验。上一版仍要求“打开本次授权页”，还让用户确认是否继续，导致初始化没有开始。

错误在我们的流程：把可选宿主工具当作通用能力，又把一次新的授权作为已有授权继续工作的前置条件。客户端代码中存在工具说明，不代表当前版本、会话或专家任务一定向模型提供该工具。本轮没有据此推断所有 WorkBuddy 版本都不支持它。

## 现在的顺序

1. 在本助理声明的连接上实际调用 `get_knowledge_context`，核对服务地址和已有库绑定，固定当前用户与库 ID。仅发现工具名称不算连接成功。
2. 校验成功，读取最新技能，执行 `start_onboarding` / `read_onboarding`。已有进度直接恢复；未选择范围则提供“检索全部文件、指定文件夹、暂不检索”，无需再确认是否沿用连接。
3. 连接缺失或明确授权失效，才走客户端正常授权。专用工具是可选项，发现不可用后不再直接尝试调用它。客户端只提供连接卡片时，请用户点击该卡片；成功后继续原任务。
4. 403、网络超时、服务故障和库不符不作为授权过期处理。不因此建立替代空间，不造 URL、不复用历史请求，不另建 OAuth 客户端冒充 WorkBuddy 连接。

首次和失效连接的正常卡片流程见 [WorkBuddy 官方连接器说明](https://www.workbuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/Connector)。该流程涉及用户授权确认，不能承诺所有客户端都可完全自动弹页。

服务端在通过认证、校验的上下文响应中新增：

```json
{
  "connection_state": {
    "status": "authorized",
    "reauthorization_required": false,
    "next_action": "read_skill_and_resume_onboarding"
  }
}
```

该字段来自实际鉴权成功的 MCP 请求，不接受客户端自报。未授权请求仍返回 401，地址或库不符仍停止。没有新增权限、扫描范围或远程工具。

开始页安装请求改为：

```text
请使用 expert-manager 下载并原样安装知序助理包：
https://zhixu.110-lab.cn/v1/assistant/package
装好后按技能开始初始化；已有有效连接直接继续，未连接时发起正常授权。
```

## 验证结果与边界

- 隔离数据库回归 74 项通过。真实 HTTP MCP 测试中，两个独立用户均仅用既有 OAuth 授权读取新连接说明、开始和读取初始化，返回三个范围选项；测试客户端未实现 WorkBuddy 专用连接工具，没有第二次授权、扫描或上传。
- 正式 HTTPS 下，原有令牌、Cookie、CSRF 和文件会话仍可访问同一合成空间；上下文返回“无需重新授权”，服务端技能为 0.13.8，初始化状态可读。原 Word 文件、目录及用户、来源、初始化、知识对象内容摘要保持不变。
- 正式页面的开始页、安装包与摘要校验、帮助、文件入口、过期提示和移动滚动检查通过。前端构建 revision 为 `zhixu-14f4fe2f0a55`，新增 TypeScript 诊断为 0；上游原存 127 条诊断未在本轮清理。
- 助理包与本机已安装助理均通过 WorkBuddy 自带校验；本机只更新与原 0.13.7 完全一致的四个说明/版本文件，保留未修改的 MCP 配置和其他专家项。
- 本轮没有操作真实 WorkBuddy 模型完成新一轮对话，也没有证明该客户端一定自动打开首次授权页。这两项为 `NOT_RUN`；上述协议测试不能替代模型行为验收。

已打开的对话可能记住旧指令。可以在原对话发送：**“读取服务端最新技能，沿用已校验的连接继续初始化，无需重新授权。”** 服务端 `read_assistant_skill` 立即返回新说明，无需教师重新安装。
