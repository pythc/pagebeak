## 使用流程

用户在 WorkBuddy 说“把这份文件放进我的知识库并整理”后，助手先核对目标知识库，再执行 prepare_file_upload。宿主正常文件工具将获准的指定原件复制到返回的私有收件目录，然后执行 upload_file。中间复制由助手完成，用户不需要复制命令或理解 MCP。单纯要求阅读附件不视为长期保存授权。

原件收到后，助手通过 get_job 等待后台解析，再读取共用目录和原文确认结果。上传成功、解析成功、能够检索是分别核验的状态。上传不要求宿主先安装 PDF 解析器、OCR 或把原件转成摘要；解析交给知识库后台。

| 工具 | 作用 |
| --- | --- |
| prepare_file_upload | 核验本库、查询容量及实际限制，建立私有收件目录 |
| upload_file | 原字节分块上传，返回来源、任务及上传会话标识 |
| read_file_upload | 查询上传状态、总大小与服务端已接收位置 |
| cancel_file_upload | 取消未完成上传并释放预留；不删除已入库来源或本机文件 |

## 实现与边界

- 复用 /v1/uploads 管线，上限 2 GiB（2,147,483,648 字节），每块最多 8 MiB；管理员配置更低时按更低限制执行。上传预留完整容量，空间不足时拒绝。
- 同一租户内，以 request_id 绑定文件元信息和 SHA-256。同一次操作重试恢复服务端位置，不重复创建来源或预留配额；变更字节或参数必须使用新请求。不同请求不自动合并相同内容。
- 完成前由服务端再次计算 SHA-256，错误字节不能入库；客户端核验返回的摘要和长度。原件保留，解析和目录走已有增量处理，不把生成摘要当作原始来源。
- 一次调用对丢失分块响应最多进行两次恢复。其余失败返回 upload_id，沿用相同文件和 request_id 可继续；用户放弃时可取消。未完成会话按现有 24 小时到期规则释放，上传期间本机文件变化会停止并尝试取消。
- 收件目录为 ~/.zhixu-file-inbox/知识库UUID/，权限 0700。只接受该目录直接子文件，拒绝任意路径、隐藏文件、目录、软硬链接及特殊设备；不扫描用户磁盘，不改变宿主保护设置。只适用于与附件同电脑的 stdio 连接，远端服务不能借此读取用户设备。
- 不删除用户本机原件，也不自动删除收件副本。文件收录归属默认 reference，仅用户明确说材料描述本人时才用 self；个人事实仍需既有复核流程。
- 复用现有幂等表，无数据库迁移，当前仍为 0016。Skill 源码和新生成包的资料收录说明已更新；未直接覆盖已安装专家的技能缓存。旧缓存中的能力清单可能滞后，以实际工具发现和 prepare_file_upload 返回的流程为准。
